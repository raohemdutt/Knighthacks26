# 4-bit decode of the teacher on gfx1151: where the time goes, the roofline, and what each kernel change should buy in joules per token

Prediction note for the kernels track, written for Task Board task R37 (thinking sitting 1) on 2026-10-11. It restates the gfx1201 analysis of `lab/refine/research/kernels/w4a16_decode_gfx1201.md` for the Strix Halo in the SJC pods (Radeon 8060S, gfx1151, RDNA 3.5, 40 CUs, 64 GB LPDDR5X shared with the CPU) serving `RedHatAI/Qwen3.8-27B-INT4` on vLLM b1388b1 plus `lab/vllm-gfx1201.diff`, ROCm 7.13, torch 2.9.1+rocm7.13.0, Triton 3.5.1. It covers the mechanism of today's W4A16 path, a roofline at batch 1, 4, 8, 16 and 64, and a predicted gain, confidence and kill criterion for each Triton config change and for the HIP route. Prefill, the vision encoder and the training lane are out of scope (the training step is `train_step_gfx1151.md`).

This is a prediction ahead of the profile. The R47 decode profile (`lab/profile_decode.py`, merged in PR #274 as e591cb1) is built and tested on a synthetic fixture only; its pod run has not happened, so no kernel time, grid or LDS byte count of the real teacher is in git yet. Every number below is either a committed measurement (the R33 chip sheet, the R26 batching rows, the R29 pod C rows), a line of code read at a pinned commit, or arithmetic on those, and each says which. Where the R47 run would settle a number, the finding names the field of its result that does.

## 1. Which kernel runs today

- **[practitioner]** At b1388b1 vLLM's ROCm mixed-precision list is Conch then ExLlama, the first kernel whose `can_implement` passes wins, ExLlama refuses bfloat16 activations, and the teacher is served with `--dtype bfloat16`, so `ConchLinearKernel` serves every 4-bit layer; `ConchLinearKernel.can_implement` checks only the weight type, the group size and that the `conch` package is installed, and `apply_weights` flattens the activations to `x_2d` of shape `[M, K]` (M = the tokens in the step, the batch size at decode) and calls `conch.ops.quantization.gemm.mixed_precision_gemm`. Source: [S07] vLLM `mixed_precision/conch.py` at b1388b1, `can_implement` and `apply_weights` (re-opened 2026-10-11); `lab/refine/research/kernels/w4a16_decode_gfx1201.md` section 2.1 (the list order and ExLlama's float16 rule, [S06], [S08]).
  - Implication: the kernel that decides J/token at decode is one Triton kernel, Conch's `_gemm_kernel`, at M = 1 to 64; the bf16 `lm_head` is not on this path (it is a dense linear, measured separately in finding 4). R47's result names the class from the serve log (`Using <Kernel> for <Scheme>`), which confirms or kills this finding.
  - Candidate experiment: KP0, the R47 pod run on pod D as merged (`python -m lab profile-decode pod-script`, one 30-minute GPU Queue slot), reading its "quantized-matmul kernel vLLM chose" field. Expected movement: none in J/token; the field names `ConchLinearKernel` and Conch's `_gemm_kernel`. Minimum sample size: 1 run (batch 1 and batch 4 phases). Confidence: high (0.9).

- **[practitioner]** Conch 1.2.1 launches `_gemm_kernel` with one fixed set of tuning parameters for every device and shape, `cxpr_block_size_m` 128, `cxpr_block_size_n` 64, `cxpr_block_size_k` 64, `cxpr_group_size_m` 16, `num_warps` 8, `num_stages` 2, on a one-dimensional grid of `cdiv(m_dim, 128) * cdiv(n_dim, 64)` programs; each program loops `cdiv(k_dim, 64)` times, loads a 64 x 64 block of packed weights and its scales, dequantizes it in registers (`_dequantize`: shift, mask, convert, subtract the bias, multiply by the scale), loads a masked 128 x 64 block of activations and calls `tl.dot(a, b, acc=acc)` into a 128 x 64 float32 accumulator; eviction hints are set on NVIDIA only. Source: [S10] Conch v1.2.1 `conch/kernels/quantization/gemm.py`, `_get_tuning_parameters`, `_gemm_kernel`, `_dequantize` and `mixed_precision_gemm_launcher` (re-opened 2026-10-11).
  - Implication: every config lever in this note (block sizes, wavefront count, stages) is one of these six values; vLLM's tree cannot set them, so each change is a patch to the installed package or a wrapper that replaces `_get_tuning_parameters` before the server starts, kept apart from `lab/vllm-gfx1201.diff` (kernels rubric K7 (c)). Because the function takes no argument, an M-dependent BLOCK_M (C1) needs the launcher patched too, which is still a few lines.
  - Candidate experiment: KP1, a microbenchmark on pod B that calls `mixed_precision_gemm` on the four chip-sheet shapes (K 5120 to N 6144, K 6144 to N 5120, K 5120 to N 17408, K 17408 to N 5120) at M = 1, 4, 16 and 64 with the stock parameters and with each config of the Summary table, timed like the chip sheet's dequant section. Expected movement: none in J/token by itself; it gives each config's kernel time before any server spawn, so a config that is not at least 1.3x faster than stock on the K 17408 shape at M = 1 never reaches a spawn. Minimum sample size: 15 timed repeats per shape and config, as the chip sheet uses. Confidence: high (0.8) that it runs in one 15-minute slot.

## 2. Workgroups, wavefronts and occupancy for the teacher's shapes

- **[opinion]** At decode M is 1 to 64, so `cdiv(M, 128)` is 1 and the Conch grid is N / 64 workgroups: 80 for the N = 5120 outputs, 96 for N = 6144 and 272 for N = 17408 (derived from [S10]'s grid and the shapes in `lab/refine/research/kernels/w4a16_decode_gfx1201.md` section 1.2). Each workgroup is 8 wavefronts of 32 lanes, because gfx1151 compiles wave32 by default (`wave.w32.compiled` 32 in the chip sheet) and Triton's `num_warps` counts wavefronts, so a launch carries 640, 768 or 2,176 wavefronts against 40 CUs x 32 waves per CU = 1,280 resident wave slots (`compute_units` 40 and `max_waves_per_cu` 32 in the chip sheet's device block). The K = 17408 down projection gives each of its 80 workgroups 272 sequential K steps of 2 KB of packed weights. Source: arithmetic on [S10] and `lab/refine/research/kernels/data/chipsheet-gfx1151-2026-10-11.json` (`device.rocminfo`, `wave.w32.compiled`).
  - Implication: the N = 5120 layers can occupy at most half of the chip's wave slots and the N = 17408 layers oversubscribe them about 1.7 times, so the grid alone is not what holds Conch to about 40 GB/s (finding 3 is); the chip sheet's own plain kernel reached 153 GB/s with only 96 workgroups of 4 wavefronts on N = 6144 (finding 4). Workgroup count becomes the limit only after the padding is gone, which is why split-K is listed as a follow-up in "Open questions" and not as a config change.
  - Candidate experiment: KP0's rocprof phase records grid and block for the top 25 kernels; expected grid `(N/64) x 256 lanes` for every Conch launch at batch 1 and batch 4. Expected movement: none in J/token. Minimum sample size: 1 run. Confidence: high (0.85).

- **[opinion]** Conch's stock tile is estimated to hold about 48 KB of LDS at two stages (a 128 x 64 bf16 activation block of 16 KB and a 64 x 64 dequantized block of 8 KB, double-buffered) and a 128 x 64 float32 accumulator of 32 KB per workgroup, which is 32 VGPRs per lane at 256 lanes before any operand registers; with 65,536 bytes of LDS per workgroup and per CU-half on gfx1151, that allows one such workgroup per CU at a time. At BLOCK_M 16 the activation block is 2 KB and the accumulator 4 VGPRs per lane. Source: arithmetic on [S10]'s tile and `lab/refine/research/kernels/data/chipsheet-gfx1151-2026-10-11.md`, section "LDS" (`lds.hip.shared_per_block_bytes` and `lds.hip.shared_per_cu_bytes`, both 65,536); `lab/refine/research/kernels/strix_halo_hardware.md`, section 3 (one workgroup addresses at most half of a WGP's 128 KiB).
  - Implication: none of the configs in this note risks Triton's `OutOfResources` at BLOCK_M 16; the stock tile is the one closest to the limit. The estimate is a byte count, not a compiled one, so each arm records the compiled kernel's `metadata.shared` (kernels rubric K5 (a)).
  - Candidate experiment: KP1 (above) also records `metadata.shared` and the VGPR count of each compiled config with `AMDGCN_ENABLE_DUMP=1`. Expected movement: none in J/token; stock between 40 and 56 KB, BLOCK_M 16 under 24 KB. Minimum sample size: 1 compile per config. Confidence: medium (0.5) on the stock byte count.

## 3. The mechanism: padding, not bandwidth, sets today's step

- **[opinion]** At M = 1 Conch's `tl.dot` multiplies a 128-row activation block of which 127 rows are masked zeros, so its matrix work is 2 x 128 x (weights) per step. The 4-bit layers hold 12.60 GB of int4 values plus bf16 group scales (`lab/refine/research/kernels/w4a16_decode_gfx1201.md` section 1.2), about 24.4 billion weights at 0.516 bytes each, so one decode step asks for about 6.26 TFLOP of padded matrix work; at the best dense bf16 rate the chip sheet measured on gfx1151 (42.3 TFLOP/s, `lora.bf16.lora4b.k2560_n2560.fwd`, hipBLAS through `torch.nn.functional.linear` at M 1024) that is at least 148 ms, 40 percent of the measured 370 ms step at batch 1 (1 / 2.70 tok/s per stream, `lab/refine/metrics.jsonl:67`). Put the other way, at 42.3 TFLOP/s the padded kernel can stream at most about 85 GB/s of packed weights (0.516 bytes x 42.3e12 / 256), 41 percent of the 209.5 GB/s copy rate. Source: arithmetic on [S10], `lab/refine/research/kernels/data/chipsheet-gfx1151-2026-10-11.json` (`lora.bf16.lora4b.k2560_n2560.fwd`, value 42.27 TFLOP/s, 15 repeats, spread 41.4 to 46.2) and `lab/refine/metrics.jsonl:67`.
  - Implication: on this chip Conch at decode is bound by wasted matrix work, not by memory, and Triton's `tl.dot` on gfx11 WMMA is unlikely to reach hipBLAS's 42.3 TFLOP/s, so the true padded cost is likely 150 to 300 ms. This is the root cause the gfx1201 note attributed to "too few memory requests in flight"; on gfx1151 the arithmetic puts the padding first. It also explains why per-stream speed barely falls from batch 1 to 16 in R26 (2.70 to 2.07 tok/s): every M up to 128 costs the same padded tile.
  - Candidate experiment: KP1 (finding 1) at M = 1 with BLOCK_M 128 against 16 on the K 17408 to N 5120 shape. Expected movement: Conch kernel time down 2.5x to 4x at BLOCK_M 16 (0.33 ms is the plain kernel's time on that shape). Minimum sample size: 15 repeats per arm. Confidence: medium (0.6).

- **[opinion]** The dequant arithmetic is not the limit on gfx1151: about 6 vector operations per weight (shift, mask, convert, bias, scale, convert) on 24.4 billion weights is about 147 billion operations per step, about 20 ms at one operation per lane per clock on 40 CUs x 2 SIMD32 x 32 lanes x 2.9 GHz (7.4 Tops/s), against at least 60 ms of memory time for the same weights at 209.5 GB/s, so it fits under the memory time when overlapped; and the chip sheet's plain Triton W4A16 kernel, which dequantizes the same way, runs in the same time at M = 1 and M = 16 on every shape (0.106 and 0.111 ms on K 5120 to N 6144; 0.330 and 0.343 ms on K 17408 to N 5120). Source: arithmetic on [S10]'s `_dequantize` and the chip sheet's device block (`simds_per_cu` 2, `max_clock_mhz` 2900); `lab/refine/research/kernels/data/chipsheet-gfx1151-2026-10-11.json`, section "dequant" (`dequant.w4a16.decode27b.*.bn64_bk64`, 15 repeats each); the kernel is `lab/kernels/chipsheet/chipsheet.py::_w4a16_kernel`.
  - Implication: against the fp16 matrix rate the dequant lands on the vector units, not on WMMA, and costs about a third of the memory time; a W4A16 kernel on this chip can be memory-bound without a HIP rewrite of the dequant. The 2.9 GHz is the rocminfo maximum, not a sustained clock (the pods read no clock, `lab/refine/research/kernels/strix_halo_hardware.md` section 7), so the 20 ms is a lower bound.
  - Candidate experiment: none beyond KP1; a config whose kernel time grows with M below 16 would show the dequant or the dot is the limit. Expected movement: none in J/token. Minimum sample size: 15 repeats per point. Confidence: medium (0.6).

## 4. What the chip sheet says a W4A16 kernel can reach on these shapes

- **[measured]** On pod D (gfx1151, ROCm 7.13, torch 2.9.1, Triton 3.5.1, 15 repeats each), a plain Triton W4A16 kernel (int4 symmetric, group 128, unpacked to fp16 in registers, two `tl.dot` calls per K block, BLOCK_M 16, BLOCK_N 64, BLOCK_K 64, Triton's default warps and stages) moved 153.3, 154.7, 149.4 and 139.3 GB/s of packed weights at M = 1 on K 5120 to N 6144, K 6144 to N 5120, K 5120 to N 17408 and K 17408 to N 5120, and 146.2 to 150.9 GB/s at M = 16 except the K 17408 shape (134.0); with BLOCK_N 32 and BLOCK_K 128 the same kernel moved only 38.3 to 45.9 GB/s, 3.3x slower. Large device copies ran at 207.8 to 212.1 GB/s (209.5 at 1 GiB), and the bf16 `lm_head` GEMV (K 5120 to N 248,320, M 1) read 218.7 GB/s in 11.63 ms. Source: `lab/refine/research/kernels/data/chipsheet-gfx1151-2026-10-11.json`, `derived.weight_gbs` of `dequant.w4a16.decode27b.*`, `copy.d2d.size_1gib` and `matmul.bf16.decode27b.k5120_n248320.m1`; kernel and configs in `lab/kernels/chipsheet/chipsheet.py` (`DEQUANT_CONFIGS`, `_w4a16_kernel`).
  - Implication: a Triton W4A16 kernel already reaches 64 to 75 percent of the copy rate on the teacher's shapes on this chip, about 3.7x what Conch moves in the step (finding 5), so the gap is Conch's tile, not Triton or the chip; and Triton configs are not forgiving here (3.3x between two plausible tiles), which is why every config change below is screened by KP1 first. The `lm_head` at 11.6 ms is the floor the 4-bit layers are compared against.
  - Candidate experiment: KP1, as specified in section 1. Expected movement: Conch with BLOCK_M 16 within 0.8x to 1.0x of these rates. Minimum sample size: 15 repeats per shape. Confidence: medium (0.55).

## 5. Step model and roofline

- **[opinion]** Bytes per decode step at batch B are 12.60 GB of 4-bit layers, 2.54 GB of bf16 `lm_head` and about 0.34 GB per sequence (0.30 GB of float32 Gated DeltaNet state read and written, about 0.04 GB of bf16 KV cache at the bench's prompts of up to about 1,100 tokens): 15.48, 16.50, 17.86, 20.58 and 36.9 GB at B = 1, 4, 8, 16 and 64. At the 209.5 GB/s copy rate the step cannot be shorter than 73.9, 78.8, 85.3, 98.2 and 176 ms, a ceiling of 13.5, 50.8, 93.8, 163 and 363 tok/s in total, which at R26's flat 96 W is 7.09, 1.89, 1.02, 0.59 and 0.26 J/token. Source: arithmetic on `lab/refine/research/kernels/w4a16_decode_gfx1201.md` section 1.2 (byte budget from [S25]), `lab/refine/research/kernels/data/chipsheet-gfx1151-2026-10-11.json` (`copy.d2d.size_1gib`, 209.5 GB/s) and `lab/refine/metrics.jsonl` lines 71, 77, 83, 89 and 95 (`teacher_batching.watts_avg`, 96.0 W at every batch).
  - Implication: the measured J/token is 5.2x (B = 1) to 7.5x (B = 64) above the bandwidth floor; matrix work stays under the memory time at every batch on the roofline (2 x 24.4e9 x 64 flops at B = 64 is 74 ms at 42.3 TFLOP/s, against 176 ms of memory), so the floor is a memory floor. A predicted value below this row would need a lever that changes the bytes moved (kernels rubric K8 (c)).
  - Candidate experiment: none beyond KP0, whose "achieved bandwidth" field divides the step's safetensors bytes by its time. Expected movement: none in J/token; the profile reports 40 to 45 GB/s at batch 1. Minimum sample size: 1 run. Confidence: medium (0.6).

- **[opinion]** The step model behind the Summary table: step(B) = conch(B) + rest(B), with rest(B) taken from R26's per-stream step time (370, 397, 431, 483 and 1,130 ms at B = 1, 4, 8, 16, 64) minus today's Conch time, and today's Conch time set to 315 ms, 85 percent of the batch-1 step (80 to 90 percent gives 296 to 333 ms), the same at every batch up to 64 because one 128-row tile covers them all. rest(1) is then about 55 ms, of which the `lm_head` is 11.6 ms and the Gated DeltaNet state about 1.4 ms (0.30 GB at 209.5 GB/s). Conch therefore moves about 40 GB/s today (12.60 GB in 315 ms), 19 percent of the copy rate. Source: arithmetic on `lab/refine/metrics.jsonl` lines 67, 73, 79, 85 and 91 (`teacher_batching.decode_tok_s`, 2.7021, 2.5218, 2.319, 2.0712 and 0.8854 tok/s per stream) and the chip sheet rates of finding 4.
  - Implication: the 85 percent share is the one assumption every "after" row rests on, and it is exactly what R47 measures ("the share of a step in the W4A16 matmul"). If R47 finds the W4A16 share under 60 percent, every C row's gain is overstated by roughly the missing share and the order of the queue is re-derived before any spawn. rest(64) is large (815 ms) because R26's 64-stream run mixes prefills into decode (TTFT 24 s), so batch-64 predictions move little whatever the kernel does.
  - Candidate experiment: KP0. Expected movement: none in J/token; W4A16 share of a batch-1 step between 75 and 92 percent, attention under 2 percent (as `gpu/R12_T0_PREREG.md` on branch `ctx/runtime/kernel-experiment-gfx1151` at 3ecd427 estimates, about 0.3 percent). Minimum sample size: 1 run with 20 or more decode steps per batch. Confidence: medium (0.6).

- **[measured]** R26 measured the running pod C teacher at 1, 4, 8, 16 and 64 concurrent streams (bench-v1, 2 text and 2 image prompts, 128 tokens with `ignore_eos`, temperature 0, thinking off, attach mode, T6 sampler at 1 s): total decode 2.62, 9.32, 16.36, 26.95 and 49.53 tok/s at 96.0 W average every time, so 36.66, 10.31, 5.87, 3.56 and 1.94 J/token gross (32.67 to 1.73 above a 10.44 W loaded idle); R29's single run on the same build on pod C measured 2.88 tok/s at 120.3 W, about 41.7 J/token. Source: `lab/refine/metrics.jsonl` lines 67 to 96 (`teacher_batching.*`, median of 3 repeats, low confidence) and lines 24 and 29 (R29, pod C); `lab/README.md`, section "Batching sweep on the pod C teacher (R26, Strix Halo, gfx1151)".
  - Implication: batching alone is already a 19x J/token lever on the stock kernel; every kernel change is scored at each batch size against these rows, and the flat 96 W (which the README reads as a steady package power limit) is why the "after" rows hold watts fixed. If a faster kernel lifts the package from 96 W toward R29's 120 W, J/token falls by 1.25x less than tok/s rises.
  - Candidate experiment: R20's stock matrix on pod B with 5 cold spawns per batch size is the "now" these rows stand in for. Expected movement: none; it replaces 3 attach-mode repeats with 5 cold spawns. Minimum sample size: 5 cold spawns per batch size. Confidence: high (0.8) that the cold-spawn medians land within 10 percent of these.

## 6. C1: BLOCK_M 128 to 16 at decode

- **[opinion]** With BLOCK_M 16 the padded matrix work at M = 1 falls 8x, from about 148 ms to about 18 ms at 42.3 TFLOP/s, and the kernel becomes memory-bound; at the 139 to 157 GB/s the chip-sheet kernel reaches with the same block sizes, 12.60 GB takes 80 to 91 ms, and allowing for Conch's other differences (8 wavefronts, 2 stages, its K-major packing that reloads the same group scale twice per 128 because BLOCK_K 64 is half the group) the prediction is 86 to 130 ms, central 105 ms, for B up to 16. At B = 64 BLOCK_M 16 would launch 4 M-tiles that each re-read the weights of projections up to about 44.6 MB each (`lab/refine/research/kernels/strix_halo_hardware.md` section 4) through a 32 MiB last-level cache, which would be slower than stock, so C1 uses BLOCK_M 64 there (half today's padding, about 125 ms). Predicted: batch-1 per-stream decode 2.70 to 6.3 tok/s (5.4 to 7.1), J/token 36.7 to 15.9 (14.0 to 18.3) at 96 W; 4.85, 3.01, 2.01 and 1.61 J/token at B = 4, 8, 16, 64. Source: arithmetic on [S10] (`stride_mul = cxpr_block_size_k / cxpr_group_size`, the scale load per K block), finding 4's rates and the step model of finding 5; the 32 MiB cache from `lab/refine/research/kernels/data/chipsheet-gfx1151-2026-10-11.md` (`cache.rocminfo.l3_bytes`).
  - Implication: one value in an installed package is predicted to cut batch-1 joules per token by more than half and batch-16 joules per token by 44 percent, without a rebuild, an engine change or new numerics (the same dequant and the same float32 accumulation, so outputs should match stock token for token at batch 1 except near-ties; kernels rubric K4). The 64 percent of the "now" J/token it does not remove is the remaining gap to finding 9's HIP route and to the roofline.
  - Candidate experiment: C1 as an experiment line, arms stock against `conch-blockm16` (a wrapper module that replaces `_get_tuning_parameters` and the launcher's grid with BLOCK_M = 16 when `m_dim <= 16`, else 64, imported before the engine starts), both on the teacher's build on pod B, R11 harness at batch 1, 4, 8, 16 and 64, greedy match at batch 1 with `--enforce-eager` first. Expected movement: `teacher.joules_per_token` at batch 1 from about 36.7 to 14 to 18.3 (central 15.9) and `teacher.decode_tok_s` at batch 1 from 2.70 to 5.4 to 7.1. Minimum sample size: 5 cold spawns per arm per batch size. Confidence: medium (0.6). Kill criterion: drop C1 if KP1 shows the BLOCK_M 16 kernel less than 1.5x faster than stock on the K 17408 to N 5120 shape at M = 1, or if `verdict()` on 5 spawns does not read the new arm ahead at batch 1 by more than 20 percent in tok/s, or if the batch-1 greedy match rate falls below stock's own self-match rate.

## 7. C2 and C3: wavefront count and stages, on top of C1

- **[opinion]** With a 16 x 64 output tile, 8 wavefronts give each wavefront a 2 x 64 slice of the accumulator and split the 64 x 64 dequant 8 ways; 4 wavefronts (Triton's default, the setting the chip sheet's 134 to 157 GB/s kernel ran with) halve the cross-wave reduction and synchronization per K step while 96 to 272 workgroups of 4 wavefronts still give at least 384 wavefronts per launch, so C2 is predicted to cut the C1 kernel time by 0 to 15 percent, central 8 percent: batch-1 J/token about 15.9 to 15.0 and decode about 6.3 to 6.6 tok/s. Source: arithmetic on [S10] (`num_warps` 8) and `lab/kernels/chipsheet/chipsheet.py::_dequant_body` (the launch passes no `num_warps`, so Triton's default applies); the chip-sheet rates of finding 4.
  - Implication: a small, cheap second step after C1 that the KP1 screen settles in minutes; if the screen shows under 5 percent, it is not worth spawns.
  - Candidate experiment: C2, arms C1 against C1 with `num_warps` 4, batch 1 and 16. Expected movement: `teacher.joules_per_token` at batch 1 down 0 to 15 percent against C1 (central 15.9 to 15.0). Minimum sample size: 5 cold spawns per arm. Confidence: low (0.35). Kill criterion: drop if KP1 shows the 4-wave kernel under 5 percent faster than the 8-wave one on the K 17408 shape at M = 1, or if `verdict()` does not read it ahead at batch 1.

- **[opinion]** At BLOCK_M 16 the per-stage LDS of the tile is about 10 KB, so `num_stages` 2 to 1 frees LDS the kernel no longer needs and removes one prologue, while 2 stages overlap the next 2 KB weight load with the current dot; with a memory-bound kernel and 80 to 272 sequential K steps per workgroup the two effects are both small, so C3 is predicted within 3 percent of C1 either way. Source: arithmetic on [S10] (`num_stages` 2) and finding 2's LDS estimate; R12's pre-registration reasons the same way for the attention kernel's stages (`gpu/R12_T0_PREREG.md` on branch `ctx/runtime/kernel-experiment-gfx1151` at 3ecd427, "Reasoning", item 3).
  - Implication: C3 is an LDS-headroom change, not a speed lever, and it should run only if a later kernel change (split-K, or fusing the scale load) needs the LDS; it is listed so its "no change" is predicted before anyone spends spawns on it.
  - Candidate experiment: C3, KP1 screen only (no spawns unless the screen shows over 5 percent). Expected movement: `teacher.joules_per_token` within plus or minus 3 percent of C1. Minimum sample size: 15 repeats per shape in KP1; 5 cold spawns per arm only if it passes the screen. Confidence: medium (0.5). Kill criterion: drop if the KP1 kernel time differs from C1's by under 5 percent on every shape.

## 8. C4 and C5: block N and block K, on top of C1

- **[measured]** In the chip sheet the plain Triton W4A16 kernel at BLOCK_N 32 and BLOCK_K 128 (192 workgroups on N = 6144, twice the 96 of BLOCK_N 64) ran 3.3x slower than at BLOCK_N 64 and BLOCK_K 64 on every shape and M: 0.354 against 0.106 ms on K 5120 to N 6144 at M = 1, and 1.192 against 0.330 ms on K 17408 to N 5120. Source: `lab/refine/research/kernels/data/chipsheet-gfx1151-2026-10-11.json`, `dequant.w4a16.decode27b.*.bn32_bk128` against `*.bn64_bk64` (`derived.seconds_median`, 15 repeats each).
  - Implication: more workgroups did not help and a longer K block hurt badly on this chip, but the two changes were made together, so the sheet does not say which one cost the 3.3x. C4 (BLOCK_N 32 alone) and C5 (BLOCK_K 128 alone) are each predicted worse than C1, by 5 to 15 percent (C4, central 10) and 5 to 25 percent (C5, central 15): batch-1 J/token about 16.9 and 17.4 against C1's 15.9. They are kept as one-lever screens because they split the chip sheet's confounded 3.3x, which a future Triton W4A16 kernel (vLLM's `TritonW4A16LinearKernel` after an engine update) needs to know.
  - Candidate experiment: C4 and C5, KP1 screen only, each one lever against C1. Expected movement: `teacher.joules_per_token` at batch 1 up 5 to 15 percent (C4) and up 5 to 25 percent (C5) against C1, that is worse. Minimum sample size: 15 repeats per shape; no spawns unless the screen shows one of them faster than C1. Confidence: low (0.4) on the direction of each. Kill criterion: drop each if KP1 shows it slower than C1 on the K 17408 to N 5120 shape at M = 1, which is the prediction.

## 9. C6: when a HIP dequant-matmul kernel is justified

- **[measured]** vLLM PR #40977's hybrid W4A16 kernel, measured by its authors on a Strix Halo (gfx1151, LPDDR5X-8000) at `--max-num-seqs 1`, cut time per output token 3.43x to 4.77x on four 4B to 8B W4A16 models; it routes decode with M up to 5 to a HIP skinny kernel (`wvSplitK_int4_g`) and larger M to a Triton fused-dequant GEMM with gfx1151 tile heuristics, and our b1388b1 predates it. Source: `lab/refine/research/kernels/w4a16_decode_gfx1201.md` sections 3.1 and 9, which cite [S13] (vLLM PR #40977, https://github.com/vllm-project/vllm/pull/40977) and [S170]; restated from that note, not re-opened tonight.
  - Implication: the HIP route already exists upstream for this exact chip, so "write our own HIP kernel" is never the first HIP step; porting E27 is. On the step model it would take the 4-bit layers to about 71 ms at B up to 4 (85 percent of 209.5 GB/s) and about 80 ms at 8 and 16: batch-1 decode about 7.9 tok/s and 12.5 J/token, 3.96, 2.67, 1.83 and 1.59 J/token at B = 4, 8, 16, 64. Against C1 that is a further 21 percent off batch-1 J/token, bought with a new engine commit (a new stock record, kernels rubric K1 (c)) and a rebuild.
  - Candidate experiment: C6 is E27 on T0 as the gfx1201 note specifies it, measured against C1 as well as stock. Expected movement: `teacher.joules_per_token` at batch 1 from 36.7 to about 12.5 (against C1's 15.9). Minimum sample size: 5 cold spawns per arm. Confidence: medium (0.5). Kill criterion: drop the HIP route if, after C1 (and C2 if it passed), R47 shows the 4-bit layers moving 147 GB/s or more (0.70 of 209.5) or taking under 40 percent of the batch-1 step, because the HIP kernel can then save at most about 20 ms of a 160 ms step; also drop it if the ported build fails the R21 correctness gate.

- **[opinion]** A HIP dequant-matmul kernel of our own is justified only when all three hold: (a) the best Triton config after C1 and C2 leaves the 4-bit layers under 0.70 of the copy rate (more than 86 ms of a batch-1 step for 12.60 GB), measured by R47's "quantized bytes over the W4A16 kernel's time"; (b) the 4-bit layers are still more than 40 percent of the step, so closing the gap to 0.90 of the copy rate (67 ms) would cut batch-1 J/token by at least 10 percent; and (c) the upstream HIP path (C6) cannot be ported or fails correctness on this checkpoint. The reason is the size of the prize: from C1's central 105 ms to 67 ms is 38 ms of a 160 ms step, about 24 percent of J/token at batch 1 and less at batch 16, where `rest(B)` dominates. Source: arithmetic on finding 5's step model, finding 4's rates (`lab/refine/research/kernels/data/chipsheet-gfx1151-2026-10-11.json`, `dequant.w4a16.decode27b.*`) and C1's prediction in finding 6.
  - Implication: on tonight's numbers condition (a) is likely to hold after C1 (the chip sheet's plain Triton kernel sits at 0.64 to 0.75 of the copy rate) and (b) is borderline, so the decision belongs after C1's measured result and R47's profile, not before; this keeps the lab from writing a kernel to save 20 percent that a config change and a port might already deliver.
  - Candidate experiment: none of its own; the decision reads C1's spawns, KP0's W4A16 share and achieved bandwidth, and C6's correctness gate. Expected movement: none in J/token from the decision itself. Minimum sample size: as C1, KP0 and C6. Confidence: medium (0.55) that the decision after C1 is "port C6, write nothing".
